# R026：迁移到更大 TP 引擎，加速运行中的长尾请求

状态：研究提议；首轮纯推理筛选已完成，结果为负面；跨TP迁移尚未实现。记录日期：2026-10-20（America/Vancouver）。 来源：用户在本会话提出。归属 M2
调度机制，M1 提供资源与显存条件，M3 提供权重版本就绪信息，不新增第四个核心机制。

## 解决的问题与主要思路

一批回答接近收齐时，少数长尾请求可能决定训练何时开始。增加独立推理实例不能缩短单个请求的自回归依赖链。 提前部署并预热 TP 更大的引擎，将正在运行的长尾请求及其 KV
cache 迁移过去继续生成，以缩短剩余完成时间。

新模型应优先满足低并发长尾 decode 的 TP 加速条件，而不只是大批量吞吐高。 首选待测 Qwen2.5-7B-Instruct；保留
Qwen2.5-1.5B-Instruct 为 R020 负面对照。 7B 更适合的判断目前是假设，尚无本机测试证据。

## 决策公式

`收益 = 留在原引擎的剩余时间 - (暂停确认 + KV重分片与传输 + 导入恢复 + 新引擎剩余时间)`

还需计入目标排队、预测误差、其他请求及训练受到的影响。预热使部署不在当次迁移关键路径上， 但额外卡的占用时间、权重显存和机会成本仍须统计。使用因果的剩余长度分布和实测速率，
不能用实际最终长度作为在线调度已知条件；在安全 decode 边界重新判断。

## 难点与正确性

- 两端必须是相同模型和精确相同的权重版本，tokenizer、位置编码、KV精度和布局兼容；请求绑定版本。
- 不同 TP 改变 KV head 的分片和复制关系，尤其是 GQA/MQA。按层、head、token 的逻辑位置重新分片， 不能把现有连续内存块传输直接视作跨 TP
  支持。
- 源端在确认的 token 边界暂停，同时保存已提交 token、长度、block映射、采样/RNG状态、停止条件及所需 logprob 状态。
- 所有目标 TP rank 先预留空间，再协调传输；全部导入确认后原子切换请求租约。 提交前保留源状态，失败可恢复，避免重复执行、漏 token 或双端同时执行。
- TP 变化可能改变浮点归约结果；应分别验证 logprob 误差和贪心续写，不能保证采样轨迹逐 token 相同。
- 预热引擎需要真实空闲资源，不得绕过训练显存优先及版本约束。

## 与既有记录的关系及代码位置

R020 在原 1.5B 负载中测得预热 TP2 更慢，且未实现 KV 迁移，应保留负面结果。 R001 当前是兼容的同 TP 迁移，不等于支持跨 TP。R019
提供长尾预测，R025 控制准入，R022 提供逐卡预算。 候选修改点包括
`areal/infra/controller/rollout_controller.py`、`areal/infra/kv_rebalance.py`、
`areal/infra/request_router.py` 及已有 vLLM KV handoff 实现。实现前须核对真实布局与协议。 候选研究点是面向训练就绪的跨 TP
长尾升级；创新性仍需相关工作检索，不能先称为已验证贡献。

## 分阶段验证

1. 准备固定版本模型，保存模型、镜像、软件和硬件身份。
1. 预热 TP1/TP2，使用相同 tokenized 输入和固定输出长度，测试单个长尾、小组请求，以及16/32并发。 分开记录 TTFT、decode
   TPOT、完成时间、输出数、启动成本和 NPU秒。
1. 只有剩余 decode 更快，再实现跨 TP 导入正确性测试；不同 KV 长度下测重分片、传输和逐卡显存压力。
1. 比较原地继续、重算迁移、保留 KV 迁移，以及从头就在 TP2 运行的基线；报告额外预留资源成本。
1. 接入 RL 因果调度，测批次收齐、训练循环、质量、版本正确性、误迁移和退化。开发重复实验后再独立启动正式确认。

目前没有收益结论。若不含迁移成本的 TP2 decode 已更慢，则该模型与请求形状不满足前提，应保存负面证据。
